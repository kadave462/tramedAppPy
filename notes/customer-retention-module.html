Pharmacie Tramed · Build Notes

Customer Retention Module

How it was designed, built, and debugged — June 2026

What This Module Does

Before this module, Pharmacie Tramed had no way to track which customers buy the same medication repeatedly. Patients on chronic medication (diabetes, hypertension, asthma) had no structured follow-up — retention depended entirely on the patient remembering to return.

This module adds three capabilities on top of the existing system:

  • 1. Medication schedule management — staff can register a customer and set a refill reminder schedule per product (e.g. every 30 days). The system tracks when the next reminder is due.
  • 2. Automatic pattern detection — the system analyses each customer's purchase history and automatically identifies which products they buy repeatedly, inferring the average refill interval.
  • 3. WhatsApp message generation — pre-written, personalised reminder messages for patients and reorder messages for suppliers, ready to send via WhatsApp in one click (no API needed — uses wa.me deep links).

Step 1 — Understanding the Requirements

The requirements came in as three bullet points:

- Allow creation of WhatsApp reminder schedules for chronic medication customers.
- Identify repeat customers or recurring prescription patterns from purchase history.
- Prepare message content for WhatsApp reminders and supplier reorder alerts.

Before writing any code, the scope was broken into four components that would need to be built:

  • New database models: Customer and MedicationSchedule
  • An analytics module (retention.py) for pattern detection and message generation
  • New pages: customer list, customer detail, and WhatsApp message centre
  • Updates to the existing sidebar navigation

Step 2 — Database Design

The existing Sale model had no link to any customer — all sales were anonymous. Two decisions were made:

Decision 1 — Add a Customer model

Stores name, phone, notes, and creation date. The whatsapp_number property automatically converts the Rwandan format 07XXXXXXXX to the international format 250XXXXXXXXX needed for wa.me links.

Decision 2 — Add customer_id (nullable) to Sale

Made nullable so all existing anonymous sales remain valid. Staff can now optionally link a sale to a known customer, which feeds the pattern detection.

Decision 3 — Add a MedicationSchedule model

One row per customer–product combination. Stores interval_days, last_purchase_date, and next_reminder_date. The next reminder is calculated as last_purchase + interval - 3 days (3-day early warning buffer). Has an active flag so schedules can be paused without deleting them.

Important ordering note: In database.py, the Customer model had to be defined before Sale, because Sale has a ForeignKey pointing to Customer. SQLAlchemy resolves forward references but placing them in the right order avoids potential issues.

Step 4 — Building retention.py

All business logic lives in retention.py. It has four responsibilities:

4a. detect_purchase_patterns(customer_id)

Queries sale_items joined to sales filtered by customer_id. Groups by product, counts purchases, and filters for products bought ≥2 times. Calculates avg_interval = span / (count - 1) where span is the number of days between first and last purchase. Also checks whether a schedule already exists for this product so the UI can show "Scheduled" instead of "Add Schedule".

4b. get_due_reminders(days_ahead)

Queries all active MedicationSchedule rows where next_reminder_date ≤ today + days_ahead. For each one, calculates an urgency label: overdue (past due), due_today, due_soon (within 3 days), or upcoming. Returns a list of dicts including the pre-generated message text and wa.me URL so the template only needs to render, not compute.

4c. get_supplier_reorder_messages()

Calls all_product_forecasts() from forecasting.py to get urgency and reorder quantities. Filters for critical/urgent/soon products with reorder_qty > 0, then groups them by supplier. Produces one message dict per supplier containing the supplier object, list of order lines, formatted message text, and wa.me URL.

4d. Message text generators

Two private functions: _reminder_message_text(schedule, days_until) and _supplier_order_text(supplier, lines). Both return plain strings formatted for WhatsApp (uses * for bold, line breaks for readability). The wa.me URL is built by urllib.parse.quote()-encoding the message text.

Step 6 — Templates

customers.html

Two-column layout. Left: table of all customers with active schedule count and "Due" badge if they have a reminder within 7 days. Right: inline "Add Customer" form (name, phone, notes). An amber info box at the bottom links to /messages showing the count of due reminders.

customer_detail.html

Four sections stacked vertically on the left: (1) Customer card with name, phone, notes, and a direct WhatsApp button. (2) Recurring purchase patterns detected automatically — each pattern shows product name, how many times purchased, last date, average interval, and a one-click "Add Schedule" form button if not already scheduled. (3) Active and inactive medication schedules — each has a "Renewed today" button (resets the clock) and a "Deactivate/Reactivate" toggle. (4) Purchase history — all sales linked to this customer. Right column: manual "Add Schedule" form with preset interval buttons (14d, 30d, 45d, 60d, 90d).

messages.html — The WhatsApp Action Centre

Tab-based layout with two panels: Medication Reminders and Supplier Reorders. Tab switching is handled by a 10-line vanilla JS showTab() function — no framework needed. Each message card shows: recipient, urgency badge, medication/product info, the full pre-written message in a monospace preview box, an Open in WhatsApp button (green, opens wa.me), and a Copy message button (uses navigator.clipboard.writeText with a 2-second visual confirmation).

Step 7 — Bug Found and Fixed During Testing

Bug: TypeError: object of type 'builtin_function_or_method' has no len()

The messages.html template crashed on sm.items|length.

Root cause: In retention.py, the supplier reorder dict used "items" as the key name for the list of order lines. In Jinja2, when you access sm.items on a Python dict, Jinja2's attribute lookup resolves it as dict.items — the built-in method — rather than the "items" key. This is a known Jinja2 gotcha: dot notation on dicts tries attribute access first, so any key that shares a name with a Python dict method (items, keys, values, get, update, etc.) will silently return the method object instead of the key's value.

# Before (broken)
by_supplier[sup.id] = {"supplier": sup, "items": []}
# After (fixed)
by_supplier[sup.id] = {"supplier": sup, "lines": []}

Fix: Renamed the key to "lines" in both retention.py and messages.html. Flask's debug reloader picked up both changes instantly — no restart needed.

Rule to remember: Never use Python dict built-in method names (items, keys, values) as dict keys when passing dicts to Jinja2 templates. Use bracket notation sm['items'] as an alternative, but renaming is cleaner.

Step 8 — Database Reset Process

Adding new models (Customer, MedicationSchedule) and modifying an existing one (Sale.customer_id) required resetting the SQLite database. Since this is a development environment with no migration tool (no Alembic), the process was:

# 1. Kill the running Flask process
Get-Process python | Stop-Process -Force
# 2. Delete the old database file
Remove-Item ".\instance\tramed.db"
# 3. Restart — app.py seeds fresh DB on startup
python app.py

The app.py startup logic checks if not os.path.exists(db_path) and runs seed_data.seed(app) automatically when no DB file exists. The seed function calls db.drop_all() then db.create_all() to create all tables fresh, including the new ones.

Note for production: In production, use a proper migration tool (Alembic / Flask-Migrate) instead of dropping and recreating the database. The current approach works for development but would destroy real data.

How the WhatsApp Integration Works (No API Required)

A full WhatsApp Business API integration requires API credentials, a verified business number, and message template approvals. For this phase, a simpler approach was used that works immediately with zero setup:

https://wa.me/250788123456?text=Hello+Jean%2C%0AThis+is+Pharmacie+Tramed...
  • → Staff clicks "Open in WhatsApp" on the messages page
  • → WhatsApp opens on their phone or desktop with the message pre-filled
  • → Staff reviews and taps Send

When the WhatsApp Business API is added in a future phase, the _whatsapp_url() function in retention.py is replaced by an API call to POST /messages on the WhatsApp Cloud API. The message text generation logic stays exactly the same — only the delivery mechanism changes.
